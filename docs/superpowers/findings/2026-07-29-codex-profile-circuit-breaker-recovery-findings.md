# Codex Profile 熔断恢复问题调查

## 用户现象

- 请求 `http://127.0.0.1:15721/v1/responses` 返回 HTTP 503：`所有供应商已熔断，无可用渠道`。
- 在 Codex 客户端中直接重试仍持续失败。
- 在 CC Switch 中关闭再开启该 Profile 的路由后，请求恢复。

## 现场证据

- `~/.cc-switch/logs/cc-switch.log` 在 10:20:23 至 10:21:04 记录到上游连续 HTTP 500，随后出现 `CB-004`：连续失败 4 次，熔断器由 Closed 进入 Open。
- 10:23:45 达到恢复超时后，熔断器由 Open 进入 HalfOpen；唯一探测请求在 10:23:47 收到上游 HTTP 502，随后出现 `CB-003`，熔断器立即回到 Open。
- 10:24:39 用户重新开关路由，日志记录旧 Profile 运行时停止、端口 15721 重新启动；重建后请求重新发往上游。
- 10:34:08 至 10:34:23 再次出现 HTTP 408、500、502，连续失败 4 次后再次触发 Open；10:35:11 至 10:35:29 再次开关路由并重建监听器。

## 代码链路

- 每个 Codex Profile 的 `RouteRuntime` 创建独立 `ProxyServer`，后者创建独立 `ProviderRouter`。
- `ProviderRouter` 的熔断器保存在内存 `HashMap` 中并跨请求保留。
- Profile 请求选择供应商时会先调用 `CircuitBreaker::is_available`；Open 且未到超时时不会把供应商加入候选列表，直接映射为 HTTP 503。
- 默认/当前配置为连续失败 4 次触发，Open 60 秒后才允许一个 HalfOpen 探测；探测失败会重新 Open 并重新等待完整超时。
- 关闭再开启路由会停止并移除旧运行时，然后创建新的 `ProviderRouter`；新熔断器初始状态为 Closed，所以看起来立即恢复。

## 当前判断

- 根因不是端口、CODEX_HOME 或 Codex 客户端重试缓存，而是 Profile 独立运行时中的熔断器按设计保持 Open。
- 用户在等待期内的普通重试不会访问上游；达到 60 秒后只有一个 HalfOpen 请求可探测。现场第一次探测恰好又遇到上游 502，因此再次熔断，形成“怎么重试都不行”的表现。
- 路由开关目前事实上兼任了“重建运行时并清空内存熔断状态”的手动恢复手段。

## Brainstorming 补充调查

### 新旧行为对比

- 旧全局路由先读取 `proxy_config.auto_failover_enabled`：仅在故障转移开启时按熔断状态过滤队列；故障转移关闭时直接返回当前供应商，不检查熔断器。
- 旧转发器还有第二层保护：当候选供应商只有一个时设置 `bypass_circuit_breaker = true`，发送前不申请熔断许可。
- 新增多 `CODEX_HOME` Profile 后，`CodexRouteProviderSnapshot` 始终包含主供应商和备用供应商列表；`select_codex_profile_providers` 对快照中的每个供应商无条件调用 `is_available()`。
- 因此 Profile 只配置一个主供应商、没有备用供应商时，也可能在供应商选择阶段被 Open 熔断器直接过滤。请求根本到不了转发器，旧有的“单供应商绕过熔断器”保护无法生效。
- 这不是熔断超时参数不合理，而是新 Profile 选择链路丢失了旧系统的策略边界：熔断器只属于故障转移策略，不应无条件作用于普通单供应商路由。

### 技术决策候选

| 方案 | 决策 | 理由 |
|------|------|------|
| A（推荐） | Profile 快照没有备用供应商时，选择阶段直接返回主供应商；转发阶段继续沿用单供应商绕过熔断器 | 精确恢复旧行为，改动小，保留多供应商故障转移的熔断能力 |
| B | 为 Profile 路由新增显式 `auto_failover_enabled` 字段 | 语义最显式，但需要数据库、命令、前端和迁移改动；当前“是否存在备用供应商”已经能表达策略 |
| C | 所有 Profile 路由完全禁用熔断器 | 单供应商恢复，但多供应商会反复请求已失败渠道，破坏故障转移保护 |

### 推荐边界

- `failovers.is_empty()`：仅使用主供应商，不创建、不读取、不更新熔断器状态。
- `failovers` 非空：主供应商与备用供应商都按现有熔断策略参与选择、放行和结果记录。
- 从多供应商热切换成单供应商后，新请求立刻绕过历史熔断状态；历史内存记录可以保留但不参与决策，将来重新配置多供应商时仍按既有状态工作。

## 已批准设计

- 用户确认采用方案 A：以 Profile 是否配置备用供应商作为是否启用熔断与故障转移的策略边界。
- 修复聚焦 `ProviderRouter` 的 Profile 候选选择，不新增数据库字段或前端开关。
- 测试从 Profile 运行时边界证明单供应商绕过、多供应商熔断和热切换语义。
