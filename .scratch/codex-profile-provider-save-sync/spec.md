# Codex Profile 共享供应商保存后立即同步所有引用

Status: ready-for-agent

## Problem Statement

用户在一个自定义 Codex Profile 中使用共享供应商时，编辑该供应商的 Base URL 并保存，数据库中的供应商已经更新，但该 Profile Home 的 `config.toml` 仍保留旧值。只有先切换到其他供应商、再切换回来，完整直连配置才会重新生成并使用新 Base URL。

这使“保存成功”与实际生效状态不一致：用户看到新配置已经保存，但 Codex 仍向旧端点发起请求。问题在多 Profile、运行中路由和故障转移供应商场景下还可能扩展为不同 Profile 同时使用同一共享供应商的不同版本。

## Solution

保存共享供应商时，由 Codex Profile 路由模块通过一个高层接口统一同步所有相关 Profile。该接口识别主供应商引用和故障转移供应商引用，并根据每个 Profile 的当前路由状态更新对应的 Profile 派生状态。

路由关闭的主供应商引用立即重建完整 Profile 直连配置；路由开启的主供应商引用保留本地路由接管配置，同时更新模型目录和运行时供应商快照；运行中的故障转移供应商引用只更新运行时供应商集合，不改变直连配置或模型目录。未引用该供应商的 Profile 不受影响。

交互式保存采用全引用成功或整体补偿：任一必要同步失败时，数据库、Profile Home 和运行时都恢复到保存前状态。应用异常退出造成的部分状态由启动对账以数据库中的共享供应商为权威幂等修复。整个流程不复制或修改 Profile 私有身份状态。

## User Stories

1. As a 自定义 Codex Profile 用户, I want 保存共享供应商的新 Base URL 后立即更新当前 Profile 的直连配置, so that Codex 不会继续请求旧端点。
2. As a Codex Profile 用户, I want 保存成功代表配置已经实际生效, so that 我不需要通过切走再切回来触发刷新。
3. As a 多 Profile 用户, I want 共享供应商保存后同步所有主供应商引用, so that 不同 CODEX_HOME 不会长期使用不同配置版本。
4. As a 多 Profile 用户, I want 未引用该供应商的 Profile 保持不变, so that 一次编辑不会污染无关环境。
5. As a 路由关闭的 Profile 用户, I want 系统重建完整 Profile 直连配置, so that Base URL、模型和供应商相关字段保持一致。
6. As a 路由关闭的 Profile 用户, I want 新配置包含现有通用配置及应用管理内容, so that 同步供应商不会丢失受管理的共享设置。
7. As a 路由开启的 Profile 用户, I want 保存供应商时继续保留指向本地路由的配置, so that 请求路径不会意外绕过路由。
8. As a 路由开启的 Profile 用户, I want 新请求立即使用更新后的运行时供应商快照, so that 无需重启监听器或切换供应商。
9. As a 路由开启的 Profile 用户, I want 保存供应商时不中断监听器, so that 正常请求接入保持可用。
10. As a 发起在途路由请求的用户, I want 请求继续使用进入时的供应商配置, so that 请求执行途中不会切换 Base URL 或凭证。
11. As a 保存完成后发起请求的用户, I want 新请求使用新的供应商配置, so that 保存结果具备明确的生效边界。
12. As a 配置了故障转移供应商的用户, I want 保存故障转移供应商后立即更新运行时供应商集合, so that 后续故障转移不会使用旧端点。
13. As a 仅把供应商用于故障转移的用户, I want 保存它时不修改 Profile 直连配置, so that 主供应商仍然决定关闭态请求目标。
14. As a 仅把供应商用于故障转移的用户, I want 保存它时不重写模型目录, so that 主供应商继续拥有模型目录语义。
15. As a 使用官方 ChatGPT 登录的用户, I want 保存共享供应商时保留每个 Profile 的 `auth.json`, so that 独立登录身份不会被覆盖。
16. As a Codex 会话用户, I want 保存共享供应商时保留会话历史, so that 配置同步不会删除或复制私有会话。
17. As a Profile 用户, I want 不同 CODEX_HOME 的私有身份状态保持隔离, so that 一个 Profile 的更新不会改变另一个 Profile 的官方登录。
18. As a 直接编辑过 `config.toml` 的用户, I want 系统明确以共享供应商为权威重新生成受管理配置, so that 不会产生来源不明的混合配置。
19. As a 使用通用配置的用户, I want 重建直连配置时继续遵循通用配置应用规则, so that 受管理的共享设置不会因供应商保存而消失。
20. As a 使用 MCP 和统一会话能力的用户, I want 供应商保存后重新投影相应的应用管理状态, so that Profile 派生状态保持完整。
21. As a 多 Profile 用户, I want 任一受影响 Profile 同步失败时整次保存失败, so that 界面不会报告部分成功。
22. As a Home 位于外置磁盘的用户, I want 磁盘不可用时收到指向具体 Profile 和路径的错误, so that 我知道需要修复哪个环境。
23. As a Home 不可写的用户, I want 其他 Profile 和数据库恢复到保存前配置, so that 一次失败不会留下配置分裂。
24. As a 用户, I want 错误信息不包含配置正文或凭证, so that 诊断信息不会泄露秘密。
25. As a 路由状态异常的用户, I want 数据库显示开启但运行时缺失时保存被拒绝, so that 系统不会把接管配置误写成直连配置。
26. As a 路由状态异常的用户, I want 错误提示要求先停止或恢复对应 Profile 路由, so that 我有明确的修复动作。
27. As a 同时操作多个 Profile 的用户, I want 保存、供应商切换和路由开关按一致顺序串行处理, so that 并发操作不会造成丢失更新。
28. As a 同时保存和切换供应商的用户, I want 后执行的操作重新读取最新引用关系, so that 它不会使用排队前的过期状态。
29. As a 多运行中 Profile 用户, I want 每个 Profile 内部原子替换供应商快照, so that 单个请求不会看到半旧半新的配置。
30. As a 多运行中 Profile 用户, I want 系统不为严格全局同时切换而暂停所有新请求, so that 保存供应商不会制造不必要的服务中断。
31. As a 多运行中 Profile 用户, I want 保存接口返回前所有相关 Profile 都已使用新配置, so that 成功响应仍然具有可靠的一致性承诺。
32. As a 应用异常退出后的用户, I want 重启时自动修复部分更新的 Profile 派生状态, so that 我不必逐个切换供应商恢复一致。
33. As a 应用异常退出后的用户, I want 启动对账以数据库中的共享供应商为权威, so that 恢复结果可预测且可重复。
34. As a 拥有一个损坏 Profile 的用户, I want 启动对账隔离该 Profile 的错误并继续修复其他 Profile, so that 单点故障不会阻止应用启动。
35. As a 用户, I want 启动对账错误保留可诊断的 Profile 标识, so that 我可以修复权限、路径或配置问题。
36. As a 维护者, I want 共享供应商保存通过一个高层模块接口完成, so that 锁、补偿和状态分支不会散落在前端与命令层。
37. As a 维护者, I want 通用供应商模块继续负责单个供应商的校验与规范化, so that Profile 同步逻辑不会复制供应商规则。
38. As a 维护者, I want Codex Profile 路由模块拥有 Home、运行时和引用同步编排, so that 相关一致性知识集中在同一模块。
39. As a 测试维护者, I want 从高层保存接口验证完整行为, so that 测试能捕获真实用户症状而不是只覆盖内部辅助函数。
40. As a 测试维护者, I want 回归测试使用临时 Home 和内存数据库, so that 测试不会读写真实 CODEX_HOME。
41. As a 测试维护者, I want 测试在秒级内确定运行, so that 该缺陷可以被持续、可靠地捕获。
42. As a 后续开发者, I want 领域词汇明确区分主供应商引用、故障转移供应商引用和 Profile 私有身份状态, so that 新增功能不会错误扩大同步范围。

## Implementation Decisions

- 共享供应商是一个或多个 Codex Profile 共同引用的权威供应商配置；Profile Home 中的对应配置属于 Profile 派生状态。
- Codex Profile 路由模块提供一个高层“保存共享供应商并同步引用”接口。调用方只传入待保存的供应商及必要标识，不负责发现 Profile、判断状态、排序加锁、补偿或刷新运行时。
- Tauri 命令层只调用该高层接口并转换错误；前端继续使用现有供应商更新调用，不新增多步同步编排。
- 通用供应商模块继续负责单个供应商的校验、规范化、通用配置存储规则和持久化语义。Codex Profile 路由模块复用这些能力，不复制供应商规则。
- 高层接口同时查询 Profile 主供应商引用和 Profile 故障转移供应商引用，并在取得锁后重新读取引用与路由状态，避免使用排队前的过期数据。
- 多 Profile 锁按稳定顺序取得。保存、供应商切换、路由启停和恢复操作使用兼容的锁顺序，避免死锁。
- 路由关闭且存在主供应商引用时，使用更新后供应商的有效设置重建完整 Profile 直连配置和主供应商模型目录。
- 有效设置必须遵循现有通用配置、统一会话及其他应用管理内容的组合规则，不直接把数据库中的原始存储形态写入 Home。
- Profile 直连配置以共享供应商为权威。Home 中未写回供应商或通用配置的来源不明手工修改不承诺保留。
- 路由开启且存在主供应商引用时，不把供应商 Base URL 写入接管中的 `config.toml`；保留本地路由目标，只刷新主供应商模型目录及运行时供应商集合。
- 路由开启且仅存在故障转移供应商引用时，只重建运行时供应商集合；不修改 Profile 直连配置或模型目录。
- 路由关闭且仅存在故障转移供应商引用时，不修改该 Profile Home，因为故障转移供应商不决定关闭态直连配置。
- 运行时供应商更新使用不可变快照替换。已经进入转发过程的在途路由请求继续使用旧快照，保存完成后的新请求使用新快照。
- 不重启监听器，不主动取消、迁移或重试在途路由请求。
- 每个 Profile 内部的运行时切换必须原子。多个 Profile 不要求在同一个瞬间切换，也不建立暂停新请求的全局屏障。
- 所有可失败的配置解析、计划构造和必要文件准备在运行时切换前完成。保存成功返回前，所有相关 Profile 必须完成收敛。
- 正常交互式保存采用全引用成功或整体补偿。任一相关 Profile Home 不可写、必要配置无效、数据库提交失败或运行时状态不满足条件时，整次保存失败。
- 补偿范围覆盖已经更新的 Profile Home、模型目录、数据库供应商和可恢复的运行时快照，恢复到保存前可观察状态。
- 路由记录为开启但对应运行时不存在时，交互式保存失败并报告状态不一致；不得把该 Profile 当作普通关闭态处理。
- 错误必须包含足以定位问题的 Profile 名称和 Home 路径，但不得包含配置正文、API Key、监听器令牌或其他凭证。
- Profile 私有身份状态不属于同步范围。`auth.json`、会话历史及其他私有身份数据不得被读取后复制、替换或清理。
- 第三方供应商凭证继续遵循现有 Codex 直连配置投影规则；该能力不得改变官方 ChatGPT 登录文件的所有权。
- 不新增跨文件系统事务日志，也不为此变更新增持久化 schema。
- 启动对账扩展为依据数据库中的共享供应商、Profile 供应商引用和路由状态幂等重建 Profile 派生状态。
- 启动对账对路由关闭的主供应商引用重建完整直连配置，对路由开启的 Profile 恢复接管配置、运行时供应商集合和模型目录。
- 启动对账中的单个 Profile 失败被隔离并记录，后续 Profile 继续处理，应用启动不因单个损坏 Home 整体失败。
- 交互式保存与启动对账具有不同失败策略：前者保证成功响应的全引用一致性，后者优先保证整体可启动和最终收敛。
- 现有前端供应商编辑交互、Tauri 参数形态和 Profile 私有身份文件格式保持兼容。

## Testing Decisions

- 唯一主要测试缝隙是 Codex Profile 路由模块的高层“保存共享供应商并同步引用”接口。测试通过该接口观察数据库、临时 Profile Home、模型目录和运行时行为。
- 主要回归测试不得直接测试私有计划构造函数、锁实现或补偿辅助函数；这些属于高层接口隐藏的实现。
- 测试使用内存数据库、临时 Profile Home、可观察运行时替身和可注入的文件失败点，不访问真实 CODEX_HOME、网络或真实监听端口。
- 首要回归场景：路由关闭的自定义 Profile 以旧 Base URL 生成直连配置，保存主供应商的新 Base URL 后，数据库和 `config.toml` 均立即包含新值且不再包含旧值。
- 首要回归场景必须证明无需切换到其他供应商再切回，直接一次保存即可生效。
- 多主引用场景验证所有路由关闭的 Profile Home 同步到新配置，未引用 Profile 的文件字节保持不变。
- 路由开启的主引用场景验证 Home 继续指向本地路由，运行时主供应商快照及模型目录更新为新版本。
- 路由开启的故障转移引用场景验证运行时故障转移供应商更新，同时 Home 与主供应商模型目录保持不变。
- 路由关闭的故障转移引用场景验证 Profile Home 完全不变。
- 在途路由请求场景验证旧请求保持旧快照，新请求在保存完成后使用新快照，监听器未重启。
- 多运行时场景验证每个 Profile 内部快照原子替换，并且保存成功返回时所有相关运行时已经收敛；测试不要求跨 Profile 同一时钟瞬间切换。
- Home 不可写场景验证整个保存失败、数据库未保留新供应商、已写入的其他 Home 和模型目录被恢复。
- 数据库提交失败场景验证所有文件与运行时恢复到保存前可观察状态。
- 路由记录开启但运行时缺失场景验证保存失败，并且任何 Profile Home、数据库和其他运行时都没有留下新版本。
- 错误输出测试验证包含失败 Profile 标识和路径，同时不包含 API Key、配置正文或监听器令牌。
- Profile 私有身份测试在保存前写入独特的 `auth.json` 和会话文件，保存后断言文件字节完全不变。
- 手工 Home 修改场景验证受管理直连配置按共享供应商重建，同时通用配置和应用管理投影遵循现有规则。
- 并发场景通过受控锁或屏障验证保存与供应商切换、路由启停串行执行，后执行者基于最新引用状态产生结果。
- 启动对账测试覆盖崩溃发生在首个 Home 写入后、多个 Home 写入后和数据库提交后的可恢复状态，并验证最终都收敛到数据库权威版本。
- 启动对账隔离测试使一个 Profile Home 持续失败，验证其他 Profile 仍被修复且失败 Profile 留下可诊断错误。
- 既有供应商更新命令层模型目录测试、Profile 关闭态供应商切换测试和 Home 配置计划测试作为先例保留；新增高层测试替代对新编排内部步骤的重复断言。
- 前端和 Tauri 命令仅保留契约透传与错误展示测试，不复制高层事务的完整场景矩阵。
- 所有回归测试必须确定、可无人值守执行，并在依赖完成编译后以秒级反馈。

## Out of Scope

- 修改 Claude、Gemini、Grok Build、OpenCode、OpenClaw 或其他应用的供应商保存行为。
- 为多个运行中 Profile 建立严格的全局同时切换屏障或暂停所有新请求。
- 主动取消、迁移或自动重试在途路由请求。
- 引入跨文件系统事务日志、分布式事务协议或新的持久化 schema。
- 自动导入或保留 Profile Home 中来源不明、未写回共享供应商或通用配置的手工修改。
- 复制、合并、迁移或清理 `auth.json`、会话历史及其他 Profile 私有身份状态。
- 改变供应商删除规则、Profile 删除规则、故障转移选择算法、熔断策略或用量统计规则。
- 修改供应商编辑 UI、Profile 管理 UI 或现有 Tauri 调用参数。
- 为启动对账中的单个失败阻止整个应用启动。
- 改变模型目录由主供应商决定的领域规则。

## Further Notes

- 已通过最小命令层反馈环复现原始缺陷：供应商更新调用返回成功，数据库包含新 Base URL，但主引用 Profile Home 的 `config.toml` 仍保留旧 Base URL。
- 对照测试证明主引用 Profile 的模型目录能够同步，说明引用发现并未遗漏；数据库断言也证明新 Base URL 没有在保存前被旧值覆盖。
- 现有供应商切换路径会生成完整 Profile 直连配置，因此“切走再切回来”能够修复文件，这与用户观察一致。
- 根因是当前保存路径只向主引用 Profile 投影模型目录指针，而通用供应商更新只识别全局当前供应商，无法补写自定义 Profile Home。
- 本规格采用项目领域词汇“共享供应商”“Profile 主供应商引用”“Profile 故障转移供应商引用”“Profile 直连配置”“Profile 派生状态”“Profile 私有身份状态”和“在途路由请求”。
- 相关架构取舍记录在 accepted ADR“Codex Profile 派生状态由共享供应商统一收敛”中。
