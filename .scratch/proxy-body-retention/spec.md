# Proxy Body Dump 全局按日清理

## 问题陈述

CC Switch 的 body dump 日志从单一目录迁移为按 Codex Profile 分目录后，原有清理仍只扫描当前请求写入的目录。结果是旧根目录、不活跃 Profile 和已删除 Profile 的历史日志无法进入清理路径，即使应用持续产生新 dump，也会长期占用磁盘。

## 目标

- 将“一天一清”恢复为整个 `proxy-bodies` 日志树的统一 retention contract。
- 应用启动时立即收敛历史日志，并在应用持续运行期间每 24 小时再次收敛。
- 保持清理为辅助、best-effort 能力，任何失败都不影响应用启动、维护循环或代理请求。
- 只删除能够严格证明为 CC Switch 生成且已经过期的标准 body dump 文件。

## 非目标

- 不限制当天日志的总容量或单 Profile 容量，避免在排障期间淘汰同日证据。
- 不删除空目录、畸形日志、其它扩展名、symlink、特殊文件或第二层内容。
- 不实现无限递归扫描或对抗已拥有日志目录写权限的恶意本地进程。
- 不增加进程内或跨进程文件锁。
- 不改变 body dump 的内容、脱敏、采样、命名或启用开关语义。

## 解决方案

由应用级 maintenance 生命周期统一拥有 body dump retention。清理从日志根目录开始，只检查根层普通文件和恰好一层真实 Profile 目录中的普通文件。标准 dump 文件的日期早于本地今天时删除；当天和未来日期保留。应用启动立即执行一次，现有 24 小时 maintenance 循环随后继续执行。请求写入路径不再扫描历史日志。

## 用户故事

1. 作为长期使用 CC Switch 的用户，我想让所有 Profile 的过期诊断日志自动清理，从而避免不活跃 Profile 持续占用磁盘。
2. 作为从旧版本升级的用户，我想让旧根目录中的历史 dump 在首次启动时自动收敛，从而无需手动寻找遗留文件。
3. 作为排障用户，我想完整保留当天日志，从而保有本次诊断所需的全部上下文。
4. 作为谨慎的用户，我想让未知文件和目录保持不变，从而避免清理逻辑误删人工材料。
5. 作为应用用户，我想让清理失败不影响代理和启动，从而使辅助日志维护不会拖垮核心功能。
6. 作为维护者，我想看到有界的清理错误摘要，从而既能诊断失败又不会遭遇告警风暴。

## 可观察 Requirements

- `REQ-01`：一次清理必须覆盖日志根层以及恰好一层的所有真实 Profile 目录，不依赖 Profile 是否活跃、存在于数据库或仍被启用。
- `REQ-02`：只有普通文件中严格匹配 `YYYYMMDD-*.log` 且日期早于本地今天的文件才可删除；当天和未来日期文件必须保留。
- `REQ-03`：应用每次启动必须立即执行一次清理，持续运行期间必须通过现有 maintenance 生命周期每 24 小时再次执行。
- `REQ-04`：清理必须独立于 body dump 构建开关；当前构建未启用 dump 时仍要收敛历史文件。
- `REQ-05`：请求处理路径不得再承担 retention 扫描或删除工作。
- `REQ-06`：symlink、特殊文件、畸形日志、其它扩展名、第二层目录及其内容、空目录必须保持不变。
- `REQ-07`：日志根目录不存在时清理必须安静完成，且不得为了清理主动创建目录。
- `REQ-08`：并发删除导致的 `NotFound` 必须视为幂等成功；其它逐项读取或删除错误不得终止剩余清理。
- `REQ-09`：非 `NotFound` 错误必须以有上限的摘要形式记录，清理失败不得阻断启动、maintenance 循环或代理请求。
- `REQ-10`：同步文件系统扫描不得阻塞应用异步运行时。
- `REQ-11`：本次修复不得增加当天容量淘汰、通用递归或跨进程锁行为。

## Scenarios

- `SCN-01`：Given 日志根层存在昨天的标准 dump，When 执行清理，Then 该文件被删除。
- `SCN-02`：Given 活跃、不活跃和已删除 Profile 对应的一层目录都存在昨天的标准 dump，When 执行清理，Then 所有目录中的过期文件都被删除。
- `SCN-03`：Given 标准 dump 的日期为今天或未来，When 执行清理，Then 文件保持不变。
- `SCN-04`：Given 根层或 Profile 层存在畸形 `.log`、其它扩展名或特殊文件，When 执行清理，Then 这些项目保持不变。
- `SCN-05`：Given 根层存在 symlink、Profile 名位置是 symlink 或真实 Profile 目录中还有第二层目录，When 执行清理，Then symlink 和第二层内容均不被跟随或删除。
- `SCN-06`：Given 日志根目录不存在，When 启动或定时清理，Then 清理成功结束且目录仍不存在。
- `SCN-07`：Given 另一进程已先删除目标文件，When 当前清理收到 `NotFound`，Then 将其计为已收敛且不产生 warning。
- `SCN-08`：Given 某个目录项读取或文件删除失败，When 清理继续，Then 其它可删除文件仍被处理，最终只产生有界错误摘要。
- `SCN-09`：Given 当前构建未启用 body dump 但历史目录存在，When 应用启动，Then 历史过期标准 dump 仍被清理。
- `SCN-10`：Given 应用连续运行超过 24 小时，When maintenance timer 到期，Then 再次执行全局清理。
- `SCN-11`：Given 多个代理请求并发到达，When 创建并写入当天 dump，Then 请求路径不扫描全局日志树，也不产生重复删除告警。
- `SCN-12`：Given 当天 dump 总量很大，When 执行清理，Then 当天标准 dump 仍完整保留，不按容量淘汰。

## 关键决策

- retention 作用域是整个固定两层日志树，而不是当前 Profile。
- 由应用启动与既有 24 小时 maintenance timer 统一触发，不由请求触发。
- 过期语义沿用本地日历日，不改为滚动 24 小时。
- 历史文件在修复版本首次启动时立即自动收敛，不设置宽限或确认框。
- 采用应用自有目录威胁模型：防误删和正常并发，不承诺对抗拥有目录写权限的恶意进程。
- 不增加当天容量上限或跨进程锁。

## 实施决策

- 建立单一的树级清理接口，输入日志根目录与本地今日日期，使遍历和保留行为能在隔离目录中验证。
- 根层只处理普通标准 dump 或进入恰好一层的真实目录；任何 symlink 与其它类型均跳过。
- 目录迭代错误必须逐项显式处理，不能通过丢弃错误的迭代适配器静默吞掉。
- 删除的 `NotFound` 是幂等成功；其它错误进入有界摘要，摘要保留总数及有限样本。
- maintenance 调用通过 blocking-task seam 隔离同步文件系统 IO，并复用现有启动与 24 小时循环。
- 新增常量进入项目统一常量模块；新增函数保持单一职责并使用中文说明。

## 错误行为与恢复

清理是 best-effort。单个文件、目录项或 Profile 目录失败不会回滚已经删除的文件，也不会阻止其它目录继续处理。不存在的根目录或被并发删除的目标视为成功。其它错误以有界摘要记录，并等待下一次启动或 maintenance tick 自动重试。清理任务本身失败不得终止 maintenance 循环。

## 兼容性

- 兼容旧版根层扁平日志与新版 Profile 子目录日志。
- 保持现有文件名、本地日期、dump 开关与跨平台标准库语义。
- 未启用 dump 的构建也会清理此前版本留下的日志，这是有意的迁移行为。
- 不引入新的外部依赖、锁文件或配置项。

## 测试决策

- 使用既有 tempfile 目录测试先建立失败的多目录回归场景，再实现树级清理。
- 断言可观察的文件存在/删除结果和错误摘要，不依赖内部遍历顺序。
- 每个 TDD slice 遵循 red → green；最终运行 body dump 定向测试、Rust 格式检查、相关类型/编译检查和项目可行的完整测试套件。
- Stage 6 必须重新运行原始旧文件 feedback loop 的受控 fixture 版本，并确认不存在临时 debug instrumentation。

## Test Seams

- `TS-01` 树级清理接口：以隔离日志根目录和确定的今日日期为输入，覆盖 `SCN-01` 至 `SCN-08`、`SCN-12`。
- `TS-02` maintenance tick 编排接口：观察启动与周期执行的任务结果，覆盖 `SCN-06`、`SCN-09`、`SCN-10`，并证明失败不阻断循环。
- `TS-03` 请求级 BodyDumper 创建接口：证明创建当天日志不触发 retention，覆盖 `SCN-11`。

## 范围之外

- 当天总量限制、按 Profile 配额、压缩、归档和 UI 配置。
- 对抗恶意本地进程的 handle-relative 文件系统实现。
- 删除空 Profile 目录或用户放入的辅助文件。
- 修改主日志 `cc-switch.log` 的轮转策略。

## 补充说明

现网证据显示旧数据主要来自 `codex-default` 和 legacy 根目录；当前活跃 Profile 的局部清理仍有效。这说明修复重点是把 retention ownership 提升到应用级，而不是修改日期比较本身。
