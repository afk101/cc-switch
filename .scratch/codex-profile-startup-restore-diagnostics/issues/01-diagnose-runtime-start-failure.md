# 01 — 打通 Profile 运行时启动失败的分阶段脱敏诊断

**What to build:** 当已开启 Codex Profile 在应用启动恢复期间无法启动 Profile 运行时时，用户和维护者可以从应用日志及路由 `last_error` 看到同一份安全诊断，明确失败属于启动恢复的“运行时启动”阶段，并区分端口绑定等稳定错误分类，而不泄露任何凭证或配置正文。

**Blocked by:** None — can start immediately

**Status:** resolved

- [x] 定义集中管理且可稳定比较的启动恢复操作标识、恢复阶段和错误分类；阶段名称不得以散落的自由文本重复定义。
- [x] 建立一份统一诊断记录，包含 Profile 标识、Profile 名称、规范 Home 路径、恢复阶段、错误分类和安全摘要。
- [x] Profile 运行时启动错误携带“运行时启动”阶段上下文传播到单个 Profile 的恢复边界。
- [x] 端口绑定失败被识别为稳定的端口绑定分类，并保留安全的监听地址、端口及操作系统错误性质。
- [x] 同一诊断记录同时驱动一条警告级应用日志和现有路由 `last_error`，两处的操作、Profile、阶段、分类和摘要保持一致。
- [x] 一个 Profile 的一次运行时启动失败只产生一条主要启动恢复诊断，不因逐层包装重复输出。
- [x] 诊断不得包含监听器令牌、API Key、Authorization、Cookie、请求或响应正文、完整供应商设置及完整配置正文。
- [x] 无法安全分类的错误使用稳定的未知分类和固定安全摘要，不直接输出未经确认的原始错误文本。
- [x] 记录诊断后继续沿用现有逐 Profile 失败隔离，不增加重试、退避、自动关闭路由、Home 回退或 `enabled` 状态变化。
- [x] 高层启动恢复测试模拟 Profile 运行时返回端口占用错误，并验证日志、`last_error`、脱敏约束和未发生重试。
- [x] 成功启动 Profile 运行时时不产生失败诊断，并保持既有运行时与 Profile 派生状态行为。

## Answer

已实现统一、分阶段且脱敏的启动恢复诊断。运行时启动错误保留类型化绑定原因，单条诊断同时写入应用警告日志与路由 `last_error`；高层测试验证端口占用、同文单事件、秘密不泄露、无重试以及健康 Profile 的既有行为。
