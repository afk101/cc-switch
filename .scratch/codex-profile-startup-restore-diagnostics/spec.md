# Codex Profile 启动恢复失败分阶段诊断

Status: ready-for-agent

## Problem Statement

用户在 macOS 登录后由开机自启启动 CC Switch 时，已开启的 Codex Profile 路由偶尔恢复失败。Profile Home 中的配置仍指向固定的本地监听端口，但对应 Profile 运行时没有成功监听，因此 Codex 客户端请求本地 `/v1/responses` 时只看到连接中断。用户手动关闭再开启路由后，重新执行生命周期操作，监听器才能恢复。

当前日志只能说明某个 Codex Profile “恢复失败”，路由记录中的 `last_error` 也只保存 Profile 与 Home 定位信息。启动恢复流程丢弃了原始失败及其发生阶段，因此无法区分凭证读取、恢复计划构造、Profile 派生状态对账、端口绑定、健康检查或运行时登记等失败。维护者只能猜测瞬时条件，无法根据下一次复现证据实施针对性修复。

## Solution

启动恢复每个已开启 Codex Profile 时，保留失败发生的稳定阶段，并把原始错误转换为不含秘密的诊断分类与脱敏摘要。同一份诊断记录同时写入应用日志和现有路由 `last_error`，其中包含 Profile 标识、Profile 名称、Home 路径、恢复阶段、错误分类和安全摘要。

本次只增强可观测性，不改变启动恢复的控制流、失败隔离、路由启用状态或 Profile 派生状态，也不增加重试、退避或自动关闭路由。用户下一次复现后，可依据具体阶段和脱敏错误单独制定修复。

## User Stories

1. As a 使用开机自启的 Codex Profile 用户, I want 启动恢复失败时留下具体阶段, so that 下一次复现不再只有笼统的“恢复失败”。
2. As a 遇到本地端口连接中断的用户, I want 错误记录指明是否发生在监听器启动阶段, so that 我能区分 CC Switch 本地监听问题和上游供应商问题。
3. As a 多 Profile 用户, I want 诊断记录包含失败 Profile 的标识、名称和 Home, so that 我能定位受影响的 CODEX_HOME。
4. As a 多 Profile 用户, I want 一个 Profile 的诊断记录不会归到另一个 Profile, so that 并发或连续恢复时证据不会串扰。
5. As a 维护者, I want 凭证读取失败具有稳定阶段标识, so that 我能检查 CC Switch 私有监听凭证存储。
6. As a 维护者, I want 待恢复状态收敛失败具有稳定阶段标识, so that 我能判断是否卡在上次未完成的生命周期补偿。
7. As a 维护者, I want 恢复计划构造失败具有稳定阶段标识, so that 我能检查 Profile 主供应商引用、故障转移供应商引用和有效设置。
8. As a 维护者, I want Profile 派生状态对账失败具有稳定阶段标识, so that 我能检查 Home 配置和模型目录写入。
9. As a 维护者, I want Profile 运行时启动失败具有稳定阶段标识, so that 我能检查监听地址、端口占用和运行时创建条件。
10. As a 维护者, I want 健康检查失败与监听器启动失败分开记录, so that 我不会把已绑定但状态异常误判为端口绑定失败。
11. As a 维护者, I want 运行时登记失败具有稳定阶段标识, so that 我能发现进程内生命周期状态冲突。
12. As a 维护者, I want 诊断信息包含有限且稳定的错误分类, so that 相同根因可以跨多次复现聚合比较。
13. As a 维护者, I want 日志保留必要的系统错误性质, so that `address in use`、权限错误、文件不存在和无效配置不会都退化成同一条摘要。
14. As a 安全敏感用户, I want 日志不包含监听器令牌, so that 本地路由认证凭证不会因诊断泄露。
15. As a 安全敏感用户, I want 日志不包含 API Key、请求头或供应商配置正文, so that 增强日志不会扩大秘密暴露面。
16. As a 安全敏感用户, I want 路由 `last_error` 遵循与应用日志相同的脱敏规则, so that UI 或数据库检查不会看到更多敏感内容。
17. As a 支持人员, I want 应用日志和 `last_error` 使用同一份诊断记录, so that 两处证据不会出现阶段或分类不一致。
18. As a 支持人员, I want 每次启动恢复失败只产生一条主要诊断事件, so that 日志不会被重复包装的同一错误淹没。
19. As a 支持人员, I want 诊断事件明确属于“启动恢复”, so that 它不会与用户主动开启、切换或关闭路由的失败混淆。
20. As a 用户, I want 某个 Profile 记录诊断失败后其他 Profile 仍继续恢复, so that 可观测性增强不会改变现有失败隔离。
21. As a 用户, I want 启动恢复成功时保持现有行为, so that 增加诊断不会改变正常开机体验。
22. As a 用户, I want 本次变更不自动重试或延迟启动, so that 先收集准确现场再决定修复策略。
23. As a 用户, I want 本次变更不自动关闭仍标记为开启的路由, so that 诊断版本不会引入新的状态转换。
24. As a 用户, I want 本次变更不重写额外的 Profile Home 内容, so that 日志增强不会影响 Profile 私有身份状态或现有配置。
25. As a 测试维护者, I want 从启动恢复的高层入口触发各阶段失败, so that 测试覆盖用户实际经历的恢复链路。
26. As a 测试维护者, I want 测试断言可观察的日志事件和持久化 `last_error`, so that 测试不绑定私有辅助函数实现。
27. As a 测试维护者, I want 测试使用内存数据库、临时 Home 和运行时替身, so that 不访问真实 CODEX_HOME 或真实监听端口。
28. As a 测试维护者, I want 每类错误的脱敏规则都有负向断言, so that token、API Key 和配置正文即使出现在原始错误中也不会输出。
29. As a 后续开发者, I want 恢复阶段标识集中定义, so that 新增恢复步骤时不会散落不一致的字符串。
30. As a 后续开发者, I want 诊断记录的构造、脱敏、日志输出和持久化职责分离, so that 后续针对日志定位问题时能够安全扩展。

## Implementation Decisions

- 继续由 Codex Profile 路由模块拥有启动恢复编排与失败诊断，因为该模块掌握 Profile 生命周期、Profile 派生状态和运行时边界。
- 为启动恢复定义集中管理的稳定阶段常量；不得在各分支内直接散落自由文本阶段名。
- 阶段至少覆盖：读取并校验 Profile、恢复待处理生命周期状态、读取路由、确保本地监听凭证、构造恢复计划、对账开启态 Profile 派生状态、创建并启动 Profile 运行时、执行健康检查、登记运行时。
- 路由不存在或路由关闭属于正常跳过，不记录为失败阶段。
- 在每个可能失败的阶段附加阶段上下文，并将错误继续向单个 Profile 的恢复边界传播；不得在中间层重复输出同一主要失败事件。
- 单个 Profile 的恢复边界将阶段化错误转换为一份诊断记录，再由该记录同时驱动应用日志和现有路由 `last_error` 更新。
- 诊断记录包含：操作类型、Profile 标识、Profile 名称、规范 Home 路径、稳定阶段、稳定错误分类以及脱敏错误摘要。
- 错误分类应基于已有错误类型和操作系统错误类别生成，而不是依赖容易误删或漏删秘密的自由文本正则。至少区分端口绑定、文件 I/O、配置或输入无效、供应商或引用缺失、恢复状态未收敛、健康检查失败、运行时状态冲突和未知错误。
- 脱敏摘要可以保留诊断所需的安全信息，例如监听地址与端口、文件路径、操作系统 I/O 类别及非秘密的配置字段名。
- 脱敏摘要不得包含监听器令牌、API Key、Authorization/Cookie 等请求头、请求或响应正文、完整供应商设置、完整配置正文及私有身份内容。
- 未知错误采用安全的兜底分类和固定摘要；不得在无法确认安全时直接输出原始 `Display` 文本。
- 应用日志采用警告级别输出单条结构稳定的主要事件，便于用户从 `cc-switch.log` 中复制并比较多次复现结果。
- 现有路由 `last_error` 字段直接保存同一诊断记录的安全文本表示，不新增数据库 schema。
- 如果写入 `last_error` 自身失败，继续记录一条不含原始秘密的独立持久化失败警告；不得覆盖主要恢复失败阶段。
- 维持现有逐 Profile 失败隔离：记录失败后继续恢复其他 Profile，启动函数仍按现有契约完成。
- 不改变 Profile 路由的 `enabled` 状态，不回退 Home，不自动停止或重新启动其他运行时。
- 不改变 Profile 私有身份状态的所有权，诊断流程不得读取、复制、替换或清理官方登录身份及会话文件。
- 新增函数遵循单一职责：阶段上下文附加、错误分类、秘密脱敏、诊断记录格式化、日志输出和持久化分别通过清晰接口组合；共用逻辑只实现一份。
- 新增注释使用中文，并保留仓库现有注释及解释性备注。

## Testing Decisions

- 主要且最高层的测试缝隙是现有“恢复全部已开启 Profile”的路由模块入口。测试从该入口触发恢复，并观察日志诊断事件和数据库中的 `last_error`。
- 测试只验证外部可观察行为：失败阶段、错误分类、脱敏摘要、Profile 定位信息、其他 Profile 是否继续恢复，以及成功 Profile 是否建立运行时；不直接断言私有辅助函数调用顺序。
- 使用内存数据库、临时 Profile Home、可控凭证存储替身和可控运行时工厂，不读取真实 CC Switch 私有目录、不修改真实 CODEX_HOME、不绑定真实端口。
- 沿用现有启动恢复隔离测试和失败运行时替身作为先例，在同一高层缝隙扩展阶段化诊断断言。
- 首要回归场景使 Profile 运行时启动返回模拟的端口占用错误，验证日志与 `last_error` 都包含“运行时启动”阶段、端口绑定分类和 Profile 定位信息。
- 健康检查场景使运行时成功启动但健康检查失败，验证其阶段和分类与端口绑定失败不同。
- Profile 派生状态对账场景使临时 Home 写入失败，验证诊断指向对账阶段并保留安全的 Home 路径和 I/O 类别。
- 恢复计划场景构造缺失主供应商引用或无效有效设置，验证记录计划构造阶段而不是运行时启动阶段。
- 本地监听凭证场景让凭证存储返回失败，验证记录凭证阶段且原始错误中注入的模拟 token 不出现在任何输出中。
- 待处理生命周期状态场景提供无效或未收敛的恢复记录，验证阶段与稳定分类正确，且不会继续启动该 Profile 运行时。
- 运行时登记冲突场景验证监听器已启动后出现的登记失败具有独立阶段，避免误报为健康检查失败。
- 失败隔离场景同时准备一个失败 Profile 和一个健康 Profile，验证失败 Profile 留下诊断、健康 Profile 仍成功恢复。
- 成功场景验证不产生失败诊断，原有监听和 Profile 派生状态行为保持不变。
- 脱敏矩阵在模拟原始错误中放入监听器令牌、API Key、Authorization 值、Cookie、配置正文和供应商设置，分别断言应用日志与 `last_error` 均不包含这些内容。
- 一致性场景验证应用日志与 `last_error` 的操作类型、Profile、阶段、分类和安全摘要相同。
- 单事件场景验证一个 Profile 的一次恢复失败只产生一条主要启动恢复诊断，不因错误逐层包装重复输出。
- 所有测试必须确定、可无人值守执行，并保持秒级反馈。

## Out of Scope

- 为启动恢复添加自动重试、退避、延迟启动或周期性自愈。
- 在恢复失败后自动关闭 Profile 路由、回退 Profile 直连配置或修改 `enabled` 状态。
- 修复端口占用、文件系统时序、恢复状态、供应商配置或其他尚未由新日志确认的具体根因。
- 改变 Codex 客户端的重试、连接或错误展示行为。
- 修改共享供应商选择、故障转移算法、熔断策略或请求转发协议。
- 新增数据库字段、诊断文件、遥测上报或远程日志服务。
- 记录请求体、响应体、请求头、供应商完整设置、配置正文或任何凭证。
- 修改 Profile 私有身份状态、会话历史或官方登录文件。
- 改变交互式路由开启、关闭、切换或共享供应商保存的既有行为。

## Further Notes

- 2026-08-04 的真实开机日志显示 CC Switch v3.19.1 启动后，`codex-api` Profile 在启动恢复阶段失败；当时 Profile Home 仍指向 `127.0.0.1:15722`，但没有对应成功监听日志。用户手动关闭再开启路由后恢复。
- 当前实现对每个 Profile 执行一次启动恢复，失败后只保存包含 Profile 与 Home 的通用摘要，并丢弃具体错误；因此本规格优先修复诊断证据缺失。
- Profile 本地监听凭证早于本次开机已存在，且存储在 CC Switch 私有目录而非 macOS 钥匙串；本规格仍保留凭证阶段，以便覆盖实际文件 I/O 失败。
- 本规格遵循 accepted ADR“Codex Profile 派生状态由共享供应商统一收敛”：单个 Profile 启动恢复失败继续隔离，不阻止其他 Profile，也不改变 Profile 私有身份状态。
- 收集到下一次真实复现的阶段与脱敏错误后，再单独制定根因修复规格；该后续规格不得提前假设必须采用重试或退避。
