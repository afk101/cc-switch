# Codex Profile 路由关闭立即停接，不等待在途请求

Status: implemented

## Problem Statement

用户显式关闭 Codex Profile 路由时，当前关闭流程会先等待在途路由请求排空，最长等待 15 秒。只要内部在途计数没有归零，界面就会持续显示关闭中；达到 15 秒后，系统仍然会继续停止监听器，因此这段等待既不能保证请求一定完成，也延迟了用户已经明确作出的关闭决策。实际日志中已经多次观察到“开始排空”到“监听器完全停止”恰好相隔 15 秒，而没有在途请求时关闭会立即完成。

## Solution

将 Codex Profile 路由关闭改为“立即停接”语义：安全恢复该 Profile 的配置后，立即拒绝新请求并停止本地监听器，不等待也不主动取消在途路由请求。已经进入转发流程的请求可以继续按关闭前的供应商快照自行结束，并允许在关闭后完成响应或写入用量记录。

保留现有监听器停止确认和失败恢复机制。正常停止应近乎立即完成；监听器异常时仍可最多等待现有的 5 秒停止确认并返回可重试错误。若 Profile 配置无法安全恢复，则关闭失败并保持路由运行，避免配置继续指向已经停止的本地端口。

## User Stories

1. As a Codex Profile 用户, I want 点击关闭路由后立即停止接收新请求, so that 我的显式关闭决策不会被后台请求延迟。
2. As a Codex Profile 用户, I want 关闭操作不再固定等待最多 15 秒, so that 路由开关能够及时响应。
3. As a 正在使用流式响应的用户, I want 在途路由请求不阻塞关闭操作, so that 一个长响应不会锁住路由开关。
4. As a 正在使用工具调用的用户, I want 在途工具调用不被关闭操作主动强杀, so that 已开始的调用可以尽力完成。
5. As a Codex Profile 用户, I want 关闭后所有新请求立即停止进入本地路由, so that 后续请求遵循已经恢复的 Profile 配置。
6. As a Codex Profile 用户, I want 关闭前已经进入路由的请求继续使用原来的供应商快照, so that 请求不会在执行途中切换供应商。
7. As a 快速重新开启路由的用户, I want 旧的在途路由请求与新运行时互不切换上下文, so that 两代运行时的供应商选择不会混淆。
8. As a 用量统计用户, I want 接受在途路由请求在路由关闭后才写入用量记录, so that 不等待关闭仍能保留已发生请求的统计结果。
9. As a Codex Profile 用户, I want 关闭前先安全恢复 `config.toml` 中受管理的路由字段, so that Codex 不会继续指向已停止的本地端口。
10. As a Codex Profile 用户, I want 关闭时保留插件、MCP、模型及其他非路由配置的最新修改, so that 关闭路由不会回滚无关配置。
11. As a Codex Profile 用户, I want 关闭操作不删除或覆盖该 Profile 的认证文件, so that 官方订阅和 Profile 私有认证保持完整。
12. As a Codex Profile 用户, I want 配置恢复失败时看到明确的关闭失败, so that 我不会误以为路由已经关闭。
13. As a Codex Profile 用户, I want 配置恢复失败时监听器继续运行, so that 当前仍指向本地端口的配置不会立即失效。
14. As a Codex Profile 用户, I want 修复配置冲突或权限问题后能够重试关闭, so that 暂时性失败不会永久破坏 Profile。
15. As a Codex Profile 用户, I want 系统确认监听器确实停止后再持久化关闭状态, so that UI 状态与端口真实状态一致。
16. As a Codex Profile 用户, I want 监听器停止失败时保留可恢复状态, so that 后续操作可以继续完成未结束的关闭事务。
17. As a 多 Profile 用户, I want 关闭一个 Profile 只影响该 Profile 的配置、监听器和状态, so that 其他 Profile 的路由继续正常运行。
18. As a 多 Profile 用户, I want 一个 Profile 的在途路由请求不会阻塞另一个 Profile 的生命周期操作, so that Profile 之间保持隔离。
19. As a 应用重启后的用户, I want 未完成关闭的恢复流程也采用立即停接语义, so that 崩溃恢复不会重新引入 15 秒等待。
20. As a 开发者, I want 所有 Profile 运行时停止路径使用同一种即时关闭规则, so that 正常关闭、失败补偿和启动恢复不会产生不同语义。
21. As a 开发者, I want 日志使用“停止接收新请求”或“开始关闭”描述该动作, so that 日志不会继续暗示系统正在等待排空。
22. As a 维护者, I want 删除不再需要的排空超时和等待契约, so that 将来不会无意中恢复隐藏的 15 秒等待。
23. As a 测试维护者, I want 关闭行为通过一个覆盖完整事务的高层接缝验证, so that 测试能够捕获真实的用户延迟而不是只验证内部函数。
24. As a UI 用户, I want 现有路由开关交互和错误提示保持兼容, so that 此修复不要求学习新的操作方式。

## Implementation Decisions

- Codex Profile 路由关闭的权威语义为“立即停接”：不再使用“优雅关闭”或“排空关闭”描述该生命周期动作。
- 保持关闭事务的现有安全顺序：获取 Profile 生命周期锁、恢复未完成操作、记录可恢复关闭事务、安全恢复 Profile 配置、拒绝新请求、停止监听器、持久化关闭状态、清除恢复记录并移除运行时。
- Profile 配置恢复成功后，运行时立即进入拒绝新请求状态；随后直接停止监听器，不读取或等待在途请求计数。
- 已经进入转发流程的请求不被主动取消。它们可以在关闭状态持久化之后继续按旧供应商快照自行结束，也可以在用户重新开启路由之后才完成。
- 保留监听器停止确认。正常停止预计立即完成；现有最多 5 秒的异常停止保护保持不变。
- 配置恢复失败继续定义为关闭失败：不停止监听器、不持久化关闭状态，并保留可重试恢复记录。
- 监听器停止失败继续定义为关闭失败：保留恢复记录和运行时托管，使后续重试可以继续停止同一个监听器。
- 正常关闭、删除前关闭、未完成关闭恢复、启用失败补偿和启动恢复中的 Profile 运行时停止应统一采用即时停接语义，不得存在隐藏的排空等待。
- Profile 运行时生命周期接口移除“等待排空”能力，并将仅负责拒绝新请求的操作使用与领域语言一致的命名表达。
- 代理服务器保留关闭边界上的新请求拒绝门禁，但移除仅供排空等待使用的在途计数、通知器和 15 秒排空超时常量；如某个计数仍被其他独立能力使用，则必须证明其用途且不得进入关闭等待链路。
- 关闭相关日志不再输出“开始排空”，改为准确表达“停止接收新请求”或“开始关闭”。
- 前端调用方式、Tauri 命令参数、Profile 路由数据库结构及持久化状态模型保持不变。
- 此变更不增加新的配置项，不允许用户重新配置等待时间，因为等待行为被整体移除。

## Testing Decisions

- 唯一主要测试接缝使用 Codex Route Manager 的关闭行为测试。该接缝能够在一次场景中覆盖真实 Profile 配置恢复、运行时生命周期调用、恢复记录和最终数据库状态。
- 主要回归场景使用临时 Profile Home、内存数据库和可观察运行时替身。替身保持一个不会自行结束的“在途请求”标记，以证明关闭操作不依赖该请求完成。
- 主要测试只断言外部行为：关闭在短且确定的时限内完成、配置已恢复、新请求门禁已启用、监听器停止已调用、路由最终持久化为关闭。测试不依赖私有辅助函数名称。
- 测试应记录并断言关键生命周期事件顺序，确保配置恢复发生在拒绝新请求和停止监听器之前，关闭状态持久化发生在监听器确认停止之后。
- 配置恢复失败场景验证监听器未停止、路由仍开启且恢复记录可供重试；这是现有高层失败测试的延续。
- 监听器停止失败场景验证路由不会被错误标记为关闭，并且下一次恢复仍能停止同一个运行时。
- 未完成关闭和启用失败补偿的恢复场景验证不会调用任何排空等待，并保持原有补偿结果。
- 已有代理服务器监听器停止超时与重试测试继续保留，因为它们覆盖的是监听器终止确认，不是请求排空。
- 现有专门验证排空等待、排空通知竞争和排空超时的底层测试应删除或替换为“关闭后拒绝新请求”的行为测试。
- 不新增前端或 Tauri 命令重复测试；它们继续验证参数透传和状态刷新，关闭时序由更高价值的 Route Manager 接缝负责。
- 回归测试必须在数秒内稳定完成，不真实等待 15 秒，也不依赖网络、真实端口或人工操作。

## Out of Scope

- 主动取消、强制中断或等待在途路由请求。
- 修改监听器停止确认的 5 秒异常超时。
- 在配置恢复失败时强制停止监听器。
- 放宽受管理路由字段的所有权校验或覆盖外部配置修改。
- 修改 Profile 路由开关 UI、Tauri 命令契约或数据库 schema。
- 修改全局代理、Claude、Gemini、OpenCode 或其他应用的关闭行为。
- 改变供应商切换、故障转移、熔断器或用量统计规则。
- 为排空等待增加可配置开关或自定义超时时间。

## Further Notes

- 本规格使用项目领域词汇“Profile 路由关闭”和“在途路由请求”。“Profile 路由关闭”表示用户显式结束路由接管并立即停止接收新请求；“在途路由请求”表示关闭前已经进入转发过程、可以在关闭后自行结束的请求。
- 现场日志已经观察到多次精确的 15 秒关闭窗口，同时也观察到没有在途计数阻塞时监听器可以在同一秒停止。这说明用户感知的随机缓慢来自排空等待分支，而不是常规配置恢复或数据库写入。
- 该方案接受一个明确后果：在途路由请求可能在 UI 已显示关闭、甚至路由重新开启之后才完成响应或记录用量；这是“不等待、不强杀”语义的预期结果。
